# School Result Processing & GPA Engine

**Team ID:** LSH26-T030
**Problem ID:** P08
**Live demo:** [Result Verification Desk](https://claude.ai/code/artifact/fd8c39cd-fa7a-4a0a-979e-63720b24be60) — a standalone dashboard seeded with this project's real 60-student dataset, built against the exact trace shape this backend returns. It is not a deployment of this repo (no hosted frontend/backend exists yet); it demonstrates the calculation, trace, and checking-list behaviour described below using the same rules and the same seed data.

## What this is

A NestJS + Prisma (Postgres) backend that computes GPA for a class of students from theory/practical subject marks, plus a Next.js frontend that consumes it. Grading follows a 6-compulsory-subject + 1-optional-subject model with theory/practical part-pass rules, absence handling, a compulsory-failure override, and a capped 5.00 GPA scale.

## Setup and run

Requires Node.js and a Postgres database.

```bash
# 1. Backend
cd backend
npm install
# create backend/.env with:
#   DATABASE_URL="postgresql://user:password@localhost:5432/schooldb?schema=public"
npx prisma migrate deploy      # apply the schema
npx prisma db seed             # seed 9 subjects + 60 students (2 classes)
npm run start:dev              # API on http://localhost:3000

# 2. Frontend (separate terminal)
cd frontend
npm install
# create frontend/.env.local with:
#   NEXT_PUBLIC_API_URL=http://localhost:3000
npm run dev                    # UI on http://localhost:3001 (or next free port)
```

Backend tests: `cd backend && npm run test` (see [Decisions and trade-offs](#decisions-and-trade-offs) — this currently only runs the default NestJS boilerplate test, not the grading logic).

## Proof each requirement is met

### (a) 60 students across two classes, 8+ edge cases

- `backend/prisma/seed.ts` seeds exactly **60 students**: **31 in class "10A"**, **29 in class "10B"** (verified by simulating the roll-increment loop).
- 11 of the 60 are hand-written edge cases (lines 49–125), each commented with its intent: a clean pass, a compulsory practical failure, a compulsory theory failure, a compulsory absence, an optional absence, an optional grade point at/below 2, an optional grade point above 2, an all-100s GPA-cap case, multiple simultaneous compulsory failures, and a combined absence + practical failure — 11 named scenarios, exceeding the 8+ ask.
- The remaining 49 are generated by `generateFillerStudents()` (same file, lines 129–158) to reach the 60-student total.

### (b) The calculation

- `backend/src/result/result-engine.service.ts` is the entire engine: `markToGradePoint()` (mark → grade point banding), `evaluateSubject()` (per-subject pass/fail + grade point, checking absence → theory/practical part-pass → band, in that order), and `computeTrace()` (aggregates the 6 compulsory grade points + the optional bonus, divides by 6, applies the compulsory-failure override, caps at 5.00, and maps to a letter grade via `gpaToLetter()`).
- **Independently verified**, not just read: 58 constructed test cases were compiled with `tsc` and run directly against this exact source file (see [Decisions and trade-offs](#decisions-and-trade-offs) for what wasn't yet made a permanent part of the test suite). Every boundary (79/80, 39/40, 32/33, practical exactly 8, theory exactly 25), the optional-bonus floor at 0, the divisor always being 6, the compulsory-failure override, and the GPA cap all passed.

### (c) The per-student trace

- `GET /students/:id/trace` (`backend/src/students/students.controller.ts` line 23, served by `StudentsService.getTrace()`) returns a full `ResultTrace`: every subject's theory/practical/mark-used, `wasAbsent`, `gradePoint`, a human-readable `ruleFired` string naming exactly which rule decided the grade point (e.g. `"practical 5 below pass mark 8"`, `"band 60-69"`, `"absent"`), and `failReason` where applicable — plus the compulsory grade-point list, the optional contribution as its own formula, the raw sum/divisor, and both the uncancelled and final GPA.
- Consumed by `frontend/src/app/students/[id]/page.tsx`, which renders this trace as a per-subject table with status, grade point, and rule columns, and a GPA arithmetic summary below it.
- `GET /students/:id/result` (same controller, line 18) returns the trimmed version (GPA/letter/failure reason only) for callers that don't need the full trace.

### (d) The office checking list

- `backend/src/checking/checking.controller.ts` implements four endpoints, each consumed by a corresponding frontend page:
  - `GET /checking/optional` → `frontend/src/app/checking/optional` — students whose optional subject was absent or scored grade point ≤ 2
  - `GET /checking/practical-fail` → `frontend/src/app/checking/practical-fail` — students who failed specifically on the practical part
  - `GET /checking/absent` → `frontend/src/app/checking/absent` — every absence, compulsory or optional
  - `GET /checking/summary` → `frontend/src/app/summary` — pass rate, grade distribution, per-subject fail counts, worst-performing subject

## Bonus features implemented

Built out in the Result Verification Desk artifact (not yet part of this repo's own frontend, since it was built as a standalone exploration of the API's trace shape):

- **Class overview dashboard** — pass rate, grade distribution chart, subjects behind failures, a searchable/filterable roster of all 60 students.
- **Severity-sorted checking list** — every student whose result a *rule* changed rather than raw marks (compulsory failures, part-only failures, absences, optional-contributes-nothing), sorted by how alarming the case is (highest raw would-have-been average first among compulsory failures), not by final GPA — since every failure ties at 0.00 and that ordering would be meaningless.
- **Near-miss flags** — any subject within 2 marks of a pass boundary (25/33/8) is flagged, since that's where a typo hides.
- **Implausible-entry warnings** — a theory/practical split where one part comfortably clears its pass line while the other sits far under it is flagged as a possible transcription error (flag only, never blocks).
- **Impact preview** — for a flagged, failing subject, shows the corrected outcome ("if practical were 8, this student passes with 4.33") computed by actually re-running the real engine logic on the corrected mark, not an estimate.
- **Live recalculation** — marks can be edited in the trace view and the GPA/letter grade update immediately, computed through a client-side port of the engine that was verified byte-identical to the backend across all 60 students before being trusted for this feature.
- **Printable marksheet** — one student per page, school-report layout, print stylesheet that hides all navigation/filters/buttons.
- **Responsive layout** — a single 768px breakpoint; below it, the subject trace becomes stacked per-subject cards (no horizontally-scrolled table) and the student list becomes cards, with the GPA figure staying the largest element on the page at every width.

## Decisions and trade-offs

- **Divisor is a fixed 6, not `subjects.length`.** The data model always has exactly 6 compulsory subjects + 1 optional; the optional contributes a capped bonus rather than a 7th full slot in the average. Hardcoding 6 matches this model exactly and was chosen over a computed count to avoid silently changing behaviour if a student's mark rows are ever incomplete.
- **`Number(x.toFixed(2))` loses trailing zeros in raw JSON** (a perfect 5.00 GPA serializes as `5`, not `"5.00"`). This is a known trade-off: fixing it to always serialize as a string would change the API's response type for every consumer. The frontend and the artifact both re-apply `.toFixed(2)` at display time, so what's shown on screen is always two decimals regardless of the wire format.
- **No automated test suite for the grading logic.** `backend/src/app.controller.spec.ts` and `backend/test/app.e2e-spec.ts` are the unmodified default NestJS "Hello World" boilerplate tests — nothing exercises `ResultEngineService`, `StudentsService`, or `CheckingController`. The 58 test cases described above were run manually against the compiled source during this review, not committed as a permanent Jest suite; that would be the next thing to add.
- **The `checking/summary` endpoint's `worstSubject.code` field is a separate ad-hoc object literal**, not part of the `SubjectTrace` type — it was deliberately left with its own shape rather than importing the full trace type for a single field.
- **The Result Verification Desk (bonus features above) is a standalone artifact, not a deployed instance of this repo.** It's seeded with a snapshot of the real 60-student data and runs a verified client-side port of the engine so it can offer live recalculation and impact previews without a live backend connection. It does not auto-update if this repo's backend logic changes.

## Pre-event scaffolding, third-party code, and AI use

- **Scaffolding:** the backend was generated with `nest new` (default NestJS project structure, `backend/README.md` is the unmodified Nest starter README) and Prisma's own CLI/setup tooling; the frontend was generated with `create-next-app` (default Next.js + Tailwind template). Neither README was hand-written for this project — this root README is the first project-specific documentation.
- **Third-party code:** `backend/.claude/skills/`, `backend/.agents/skills/`, and `backend/.windsurf/skills/` contain vendored Prisma reference documentation (not executed code) that ships alongside Prisma's own tooling; it was not authored for this project and contains no project data or secrets (see below).
- **AI use, including Claude Code:** Claude Code (Anthropic) was used throughout this project's build-out after the initial scaffolding and backend logic were in place — for auditing the existing calculation engine against the stated specification, extending the trace API to expose per-subject rule detail and full GPA arithmetic, building the Result Verification Desk dashboard (including the near-miss/implausible-entry/impact-preview/live-recalculation features and the printable marksheet), fixing a frontend/backend field-name mismatch introduced by the trace API change, verifying the engine's correctness with 58 constructed test cases run against the compiled source, and writing this README. All calculation logic itself (`result-engine.service.ts`'s thresholds, banding, and formulas) predates this AI-assisted work and was reviewed, not rewritten, except for the field-naming/trace-shape refactor described above.
